# Optimizing RDD Joins (24:38)

Source: `scala/part4rddjoins/SimpleRDDJoins.scala`

## Scenario
Exam data (generated by `DataGenerator.generateExamData`, 1M candidates, 5 attempts each):
- `examIds.txt` → `RDD[(Long, String)]` (candidate id, name), read with `.partitionBy(new HashPartitioner(10))`
- `examScores.txt` → `RDD[(Long, Double)]` (candidate id, score of one attempt)

Goal: **count the candidates who passed** (at least one attempt > 9.0).

## The 5 versions compared
1. **`plainJoin`**: `scores.join(candidates)`, then `reduceByKey` to keep the best attempt, then `filter`.
   This joins **every attempt** (5x more rows than needed).
2. **`preAggregate`**: `scores.reduceByKey(Math.max)` **before** the join, so only 1 row per candidate is joined.
   About 10% faster according to the course comments.
3. **`preFiltering`**: `reduceByKey(Math.max).filter(_._2 > 9.0)` before the join, which shrinks the joined data even more.
4. **`coPartitioning`**: reuse the partitioner of `candidates` for `scores`:
   ```scala
   val partitionerForScores = candidates.partitioner match {
     case None => new HashPartitioner(candidates.getNumPartitions)
     case Some(partitioner) => partitioner
   }
   val repartitionedScores = scores.partitionBy(partitionerForScores)
   repartitionedScores.join(candidates)   // both sides share the partitioner, so no extra shuffle at join time
   ```
5. **`combined`**: co-partition, then aggregate and filter, then join.

## Concepts behind it
- A join on 2 RDDs with **the same partitioner** is a narrow dependency: matching keys already live in the
  same partition index, so the join does not shuffle.
- If only one side has a partitioner, only the **other** side is shuffled to match it.
- `reduceByKey` on an RDD that is already hash-partitioned **keeps** that partitioner, so the later join stays shuffle-free.
- Compare the versions in the Spark UI (**DAG** and shuffle read/write). They all return the same count.

## To remember
- Reduce the data **before** the join: aggregate first, then filter.
- Co-partition the two sides (same partitioner and same number of partitions) to avoid the join shuffle.
- `rdd.partitioner` tells you whether Spark knows how the RDD is partitioned.

## PySpark equivalent
`rdd.partitionBy(n)` uses `portable_hash`. Two RDDs partitioned with the same `n` and the same partition function are
co-partitioned: `rdd.partitioner` returns a `Partitioner(numPartitions, partitionFunc)` object, and two of them compare equal.
