# Reusing JVM Objects, Part 1 (24:57)

Source: `scala/part5rddtransformations/ReusingObjects.scala`, versions 1 and 2.
(How the file splits across the 2 videos is my guess: versions 1-2 here, version 3 in part 2.)

## Scenario
Text batches from many data sources, one line per record: `"35 // some text"` → `(sourceId, text)`
(file `generated/lipsum/3m.txt`, 3M lines generated by `DataGenerator.generateText`).

Stats per source id, and they must be **very fast**:
- number of lines
- total number of words
- length of the longest word
- occurrences of the word `"imperdiet"`

All versions use `aggregateByKey(zero)(aggregateNewRecord, combineStats)`. The by-key function is already the
right one, so this lesson is about **what the aggregation functions allocate**.

## Version 1: immutable case class
```scala
case class TextStats(nLines: Int, nWords: Int, maxWordLength: Int, occurrences: Int)

def aggregateNewRecord(s: TextStats, record: String): TextStats = {
  val words = record.split(" ")
  TextStats(s.nLines + 1, s.nWords + words.length,
            math.max(words.maxBy(_.length).length, s.maxWordLength),
            s.occurrences + words.count(_ == criticalWord))   // a NEW object per record
}
```
Idiomatic Scala, but it allocates **a new `TextStats` for each of the 3M records**, which means GC pressure.

## Version 2: mutable class, updated in place
```scala
class MutableTextStats(var nLines: Int, var nWords: Int, var maxWordLength: Int, var occurrences: Int)
  extends Serializable

object MutableTextStats extends Serializable {
  def zero = new MutableTextStats(0, 0, 0, 0)   // def, not val
}

def aggregateNewRecord(s: MutableTextStats, record: String): MutableTextStats = {
  ...
  s.nLines += 1; s.nWords += words.length; ...
  s                                              // return the SAME object
}
```

## Why mutating is allowed
The `aggregateByKey` / `foldByKey` / `combineByKey` docs explicitly allow the functions to **modify and return their
first argument** instead of creating a new object. Spark gives each key its own copy of the zero value
(it serializes it and deserializes a fresh copy).

## To remember
- Per-record allocations in hot aggregation code add up to millions of short-lived objects. Look at the
  **GC Time** column in the Spark UI.
- Reuse one mutable accumulator per key per partition: mutate it, then return it.
- The class must be `Serializable` because the accumulators are shuffled.

## PySpark note
In PySpark the aggregation runs in Python workers, where serialization (pickle) dominates and the JVM GC is not involved.
The same pattern (`[0, 0, 0, 0]` mutated in place) saves some allocations, but expect a much smaller gain.
